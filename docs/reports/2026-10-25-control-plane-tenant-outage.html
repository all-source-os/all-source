2. What happened

Full outage, 2026-10-24 21:51Z → 2026-10-25 10:02Z fixed at the cause

After a Core restart the write-ahead log put its first new entry into its oldest segment. Replay applied it out of order and invalidated every tenant's egress account, so every read was refused (control-plane edge: 0 × 200, 501 × 503 in ten minutes). Fixed by #351 and deployed at 10:02:28Z as sha-fe6be491; boot logs show no Invalid durable egress event and the system log recovered 569,858 events with 0 corrupted.

Read refusals and sign-in failures, ongoing user-facing

Sections 3 and 4. The egress guard refuses about one Longhand read in ten with 429, mostly when its concurrency slots are full, and sign-in reads every verification ever written in one request.

Projector reads of the control-plane tenant fixed 13:09Z by deploying #355

Update 13:15Z. Core 05466bca (#355) went live at 13:03:07Z with the 768 MiB limit (strict archive read limits max_decoded_bytes=805306368 at boot). The tenant's full history loaded in 8.5 s (139,859 events, no files skipped). The projector's first board read returned 200 at 13:09:57Z; its first change-feed call got a 502 because that 8.5 s load ran past the control plane's wait; every call after that succeeded (80 change-feed and 6 board reads with 200 by 13:16:00Z). Core memory after the load: 6.55 GB, 9.3 GB free.

Before that: Longhand's shared queue projector is a background job that pre-builds the team queue board. Its reads ask Core for the tenant's whole history, which was larger than Core's 128 MiB limit for such reads, so each one failed with 500. The board it builds is not shown to users (LONGHAND_SHARED_QUEUE_PROJECTION=false). From Longhand #1702 (11:41:17Z) it retried every 1, 2, 4 … minutes, capped at 5.

3. Sign-in failures

Cause, traced to the request: the error you saw at 10:11Z (reference aa20bcdf-68fd-4a5e-b383-7bafecaacca5) is recorded as auth.oauth.callback_failed with reason_code=verification_lookup_failed, surface=desktop, at 10:11:43.62Z. Longhand's Google callback tried its first account-store read three times (50 ms and 200 ms apart) and all three failed.

That read is get_verification_by_identifier in the auth adapter, which sends GET /api/v1/events/query?event_type_prefix=auth.verification.created&limit=10000 with no time bound: it fetches every sign-in verification ever written to find one. Same failure code at 09:55:18Z and 10:28:37Z (admin sign-ins).

5. The release speed check and #355

What the check is. Before a new Core version ships, CI starts the old Core and the new one on the same machine, sends each 256 reads of 32 events, and divides the new one's reads per second by the old one's. Below 0.80 the deploy is blocked.

What changed the number: compression, not #355. The check's client asks for gzip automatically, and the old Core it compares against has no gzip, so since gzip shipped the new Core is being timed doing extra work the old one never does.

Measured directly on one machine, alternating 13 times: #355 against its parent reads at 0.998 of the speed (0.934–1.071). The same binary with and without gzip reads at 0.730–0.777: gzip costs about a quarter of Core's raw read rate in this test. #355's changes on the read path are a startup setting and an error type of unchanged size.

Conclusion: #355 is safe to deploy. The check needs fixing so it compares like with like (both with gzip, or both without).

Measurement scripts in the session scratchpad (perf355/); the CI baseline image allsource-core:sha-a8b94f3 could not be pulled locally (private package, token lacks read:packages), so the local pairs compare #355 with its parent rather than with the CI baseline.

7. Limits ahead

Two kinds of request make Core load this tenant's entire history, so they get slower and riskier as the history grows:

What breaksWho noticesTodayAfter #355After #355 + #357
Projector reads: the background job above, which reads the tenant's change feed and its pre-built boardnobody today; users only if the shared board is switched onfails (history 585 MB > 128 MiB limit)works until history reaches 768 MiB: ~220 MB of room at ~14 MB/day, ~16 daysno longer depends on history size; remaining cap 600,000 events scanned (139,000 now, +1,550/day), ~300 days
Ordinary reads: any query that needs the tenant loaded in memoryevery Longhand userworksunchanged by both; depends on memory (section 8)

If team_queue.snapshot.chunk stopped accumulating, growth would fall from ~14 MB/day to about 1.6 MB/day (26 MB over the last 16 days without it), and every runway above would grow about eight-fold.

10. What to do, in order

  1. Stop the 429s on sign-in and reads. AllSource half in this PR, not released Re-measured 20:46:45–20:49:20Z: 1,615 event reads served and 149 refused with 429 (8.4%), unchanged since midday. The refusals are bursts, not slow reads. The mean read takes 20 ms, and 32,390 requests finished in under 5 ms against 32,755 refusals in total. That fits Core's limit of 4 reads in flight per tenant (egress.rs:217) being hit by Longhand's parallel reads: seat usage and step cost each issue up to 16 at once, and the queue page up to 12. Nothing in Longhand caps the total.
    • better-auth-allsource 0.14.14: the verification and account lookups on sign-in ask Core for at most 16 matching events with a payload_filter instead of reading 10,000, still one read each. A verification's id now starts with its identifier and its tombstone repeats it, and an account's tombstone names its provider and account id, so the same filtered read returns the tombstone ahead of what it hides. A sign-in for an existing user stays at two guarded reads. Verifications created before the upgrade take a second read until they expire (OAuth state lives minutes). A consumed or deleted verification no longer counts as valid. Before, the lookup only read auth.verification.created events and never saw the tombstone, so a used sign-in state stayed valid until it expired. A 429 that names no admission scope fails that one read and no longer stops every auth read for its Retry-After.
    • Control plane: a full slot pool or Core's per-tenant limit answers 429 with Retry-After: 1 instead of 30, because a slot frees within milliseconds. Each refusal body carries a reason (pool_full, Core's busy, capacity or exhausted, or ledger_unavailable), and every refusal is logged with that reason, so the two sources can now be told apart.
    • Still to do, in Longhand: upgrade to better-auth-allsource 0.14.14 once it is published, cap the parallel reads, and label the probe from reason.
  2. Deploy #357 (merged as f29cc526 + 897623e8) before the ~16 days of room that #355 gives run out (#355 deployed 13:03Z). Fix the release check to compare gzip with gzip.
  3. Stop team_queue.snapshot.chunk from accumulating (Longhand): keep only the latest snapshot, or move snapshots out of the event history. This removes ~81% of the bytes and ~88% of the growth.
  4. Export memory per tenant from Core, so the limit on ordinary reads has a number.
  5. Fix the sign-in probe label, so a 429 is not reported as an exhausted allowance.

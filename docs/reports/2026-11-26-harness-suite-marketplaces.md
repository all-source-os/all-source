# What engineering teams can build with AllSource

An engineering team can build a harness that maps its code, remembers project decisions, tracks tasks and carries verification evidence between coding agents. The team supplies its sources, access rules and workflow. A public ChatGPT or Claude listing needs a narrower promise: connect a workspace, ask what happened to one service and inspect the records behind the answer.

## First listing: AllSource Event History

Proposed job: “Show what changed in checkout before this incident and which stored records explain it.” The user chooses an authorized workspace and service, reads a chronological answer and can open its evidence. Start with reads. An empty timeline should say which service and period were searched. Refusing a second tenant's record is part of the same demonstration. Add decision lookup when a service-to-decision link exists; add pending replay review only after the separate product flow is verified.

## What the CTO can reasonably expect

The suite can support **“Build a coding workflow that remembers your team's decisions and shows the evidence behind a change.”** A team provides the connection between its service, owner and decision record, chooses which external systems to ingest and decides who can read each record. Hound can supply code structure; it does not establish why a team made a decision. Longhand is a founder-reported implementation example. Department-wide permissions, synchronisation from a customer's tools and unaided onboarding still need demonstrations on the customer path.

The marketplace test is separate from the landing-page comprehension test. On a clean account, an engineer should be able to authorize one workspace, retrieve a real service timeline with evidence, and see access denied for another tenant. No public submission, publisher-account inspection, live hosted authorization or customer deployment was part of this assessment.

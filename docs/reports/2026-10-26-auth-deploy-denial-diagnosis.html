Why a deploy denied clients

Diagnosis of the 2026-10-26 key-enforcement deploys and what has to exist so that no deploy denies a client again without a rule that names it. Code references are at e1416e58 unless another revision is given. Incident timeline and impact: Client access outage.

Invariant. A client that was served before a deploy is served after it, unless a written rule names that client, or the kind of credential it uses, with an owner and a date. A deploy that would deny anyone else does not cut over.

1. The request path that refused clients

Every Authorization: Bearer request to the control plane goes through AuthMiddleware (auth.go:375-462). The red steps are new in the key-lifecycle change; at 7e08966d a token with a valid signature and expiry was accepted at auth.go:409.

Public path (/livez, /api/v1/admin/*, /auth/* except /auth/session)? skip auth. This is why the health check stayed green.
ask_ key? validated by Core /api/v1/auth/me; unchanged.
JWT signature and expiry (auth.go:218-244) 401 invalid token / token expired; unchanged.
credentialType (managed_keys.go:263-280): human session → accepted. Short service delegation (≤ 60 s) → accepted. Any other API-key JWT, including every key minted before the change, → treated as a managed key.
Managed key → managedKey() (managed_keys.go:138-247): a strict read of Core's apikey:<tenant> history on every request, no cache, 5 s timeout.
Core slow, down or non-200 → 401 API key authority unavailable. History incomplete → 401 incomplete API key authority. History malformed → 401 invalid API key history. No apikey.created with id = token subject → 401 unregistered or revoked API key (:235). Expired record → 401 API key expired.
Scope check (managedKeyAllows) 403 insufficient API key scope.

Every 401 goes back to the client as {"error":"unauthorized","message":…} (auth.go:426) and nowhere else.

Longhand's key is very likely a legacy onboarding key. Its tenant id has the onboard- prefix that OnboardHandler generates (onboard.go:78), and that handler signed with SignAPIKey. The prod read key used by our own tooling got the exact text unregistered or revoked API key, which only managed_keys.go:235 produces. The key's claims were not read.

Second defect, not hit today: while Core is down or slow, every API-key request gets a 401, the status that means "your credential is bad". During Core's 21:02–21:08 restart, v127 answered 401 to event reads and 0 × 5xx. An availability fault becomes an access denial, which clients treat as permanent.

4. How it shipped

  • The denial was a written decision, not an accident. "Unregistered long-lived API JWTs are rejected. This includes legacy onboarding tokens" (docs/plans/2026-10-26-api-key-lifecycle-repair.md:35), repeated in the PR #363 body. The plan named SignAPIKey as "used by onboarding" (:15). What was missing was the list of who holds such a key. No inventory, owner notice or reissue path is recorded anywhere in the repo.
  • The tests assert the denial. managed_keys_test.go:196-199 requires a long-lived unmarked key to get 401; Query Service has "markerless serviceaccounts are rejected". No test feeds a token from the pre-change SignAPIKey path and expects it to keep working.
  • The proof ran against an empty Core. The "Tenant Egress and Key Lifecycle" workflow runs revoke-across-restart on a fresh Core. The hosted proof used synthetic keys and one other tenant's existing key: "The proof covers one tenant" (verification report :128).
  • A failed post-rollout check was recorded and passed over. initialPostRolloutObservation: 401, cause "undetermined" (docs/reports/evidence/2026-10-26-legacy-admission-readback.json:47-51). PR #364: "One immediate post-rollout 401 remains unexplained".
  • Images were deployed from local trees before merge (v124–v127), and both PRs merged with zero reviews.
  • The 19:45 warning was misread. Longhand's 401 at 19:45 arrived during v125; the 19:52 diagnosis on PR #363 was about a different tenant. #364 then fixed registered keys with legacy version histories and left unregistered keys denied by design.
  • The redeploy at 22:44 was blind too. I deployed e1416e58 after its CI and proof workflow passed, without checking which live credentials it refuses, and judged the cutover by the health check.

5. How to diagnose a denial spike

Use the Fly Prometheus API for org allsource. Each control-plane process has its own counters, so compare instances, not time ranges alone.

Step 1: is the new process refusing what the old one served?

sum by (instance, path, status) (
  increase(control_plane_http_requests_total{app="allsource-control-plane",
    path=~"/api/v1/events/query|/api/v1/event-feed|/api/v1/events"}[10m]))

Today this read: old machine 10,417 × 200 on event reads; new machine 651 × 401 and 0 × 200.

Step 2: which tenant went quiet?

sum by (tenant, status_class) (
  increase(control_plane_tenant_requests_total{app="allsource-control-plane"}[10m]))

A tenant whose 2xx goes to zero while anonymous 4xx jumps is the victim. Normal anonymous 4xx is about 80 per 10 minutes.

Step 3: when did it start, per release?

max by (instance) (process_start_time_seconds{app="allsource-control-plane"})
sum by (status) (increase(control_plane_http_requests_total{app="allsource-control-plane",
  path="/api/v1/events/query"}[1m]))

Line the process start times up with the first minute of 401s. Today: v124 started 18:56:19, 401s began at 18:57.

Step 4: what reason?

Today there is no server-side record. Reproduce with the affected credential against GET /api/v1/auth/session and read the body's message, or decode the key's payload to learn its subject and kind and compare with section 2. Once safeguard 2 below exists, this step becomes one query on control_plane_auth_denials_total by reason.

6. Safeguards, ranked

Ranked by how directly each stops a deploy from denying a client that no rule names.

  1. Shadow mode for credential authority. ALLSOURCE_KEY_AUTHORITY_MODE=off|shadow|enforce, default shadow, mirroring tenant_admission.go. In shadow, a lookup that would deny is counted and logged and the request proceeds on the previous rule. enforce refuses to start unless the would-deny count over a window is zero, or every tenant it would deny is listed in a deprecation file. New file apps/control-plane/key_authority_mode.go, branch at auth.go:415-423; same switch in Query Service api_key_authority.ex. Test: copy TestAdmissionShadowChangesNoBehaviour (tenant_admission_test.go:127): the same requests return the same statuses with and without shadow, and the would-deny is recorded.
  2. Denials labelled by reason, credential kind and tenant, and logged. control_plane_auth_denials_total{reason, credential_kind, tenant}, with the tenant taken from the already-parsed claims, never anonymous. Fixed reason set: unregistered, revoked, history_invalid, incomplete_authority, authority_unavailable, expired, scope. One log line per denial with the same fields. Cardinality bounded by the existing cap in tenant_metrics.go. Test: one table case per reason asserting the counter moves.
  3. An authority outage is not a denial. When Core cannot answer the lookup, return 503 with Retry-After, not 401; optionally serve from a short positive cache of the last good answer. A client must be able to tell "your key is bad" from "we are down".
  4. Frozen compatibility fixtures. Commit tokens produced by every past minting path (SignAPIKey onboarding, agent register, trial, old dashboard), signed with a test-only key. TestPreviouslyIssuedCredentialsStillAdmitted requires 200 for each, unless docs/contracts/credential-deprecations.json lists that shape with an owner, a notice date and an end date. Run it in the lifecycle workflow. Removing a shape without an entry fails CI.
  5. Credential census before any auth deploy. An admin endpoint that reports, per tenant over the last N hours, requests by credential kind and registered-or-not (built on safeguard 2). Runbook step in FLY_IMAGE_PROMOTION.md: no cutover while any tenant shows unregistered traffic without a deprecation entry.
  6. Cutover gated on authenticated traffic. Deploy with --strategy canary, then compare 401 rate on the new instance against the old through the Prometheus API; abort and roll back if it is higher. Add an authenticated read probe with a dedicated registered canary key next to /livez. With today's numbers (651 × 401 against 0) this trips in the first minute.
  7. Alert (deploy/prometheus/auth.rules.yml): 401 ratio above 5 % for 2 minutes and three times the ratio an hour earlier; and a per-tenant rule when a tenant that was mostly 2xx becomes mostly 401. Test with promtool test rules fed today's series.
  8. Process. Production images only from merged main commits; a PR that touches auth.go, managed_keys.go, api_key_authority.ex or managed_key_access.ex needs a human review and a filled "credentials denied by this change" section.
  9. Stop minting unregistered keys. Agent registration and trial still call SignAPIKey on main; move them to IssueManagedAPIKey before any enforcement returns.

Shipped with this report: safeguard 1 as ALLSOURCE_KEY_AUTHORITY_MODE, defaulting to shadow (the lookup is cached for 30 s per key only while shadowing; enforce keeps a per-request read so a revocation acts immediately); safeguard 2 as control_plane_auth_denials_total{mode,reason,tenant} with one log line per tenant and reason per minute; safeguard 3 as a 503 with Retry-After when enforcing and Core cannot answer; and the admin Monitoring page rebuilt on client traffic (/api/v1/admin/metrics/client-health).

Order for re-enabling enforcement: safeguards 2 and 3 → shadow mode (1) deployed → Longhand and every other tenant shown by the shadow count reissued a registered key → the count reads zero for a full day → enforce, with the canary gate (6) and alert (7) in place.

1. Who was affected

Longhand, AllSource's only tenant with real traffic today. Its control plane reads and writes through one API key for tenant onboard-control-plane-at-technical-leaders-com. Longhand's status page showed Sign-in and Queue reads Down, with the reasons sign_in_read_failed and core_read_failed.

3. Cause

A policy that refuses every unregistered API key, deployed without knowing who holds one root cause

The key-lifecycle change makes the control plane accept an API key only if Core holds an apikey.created record whose id equals the key's subject, with no later revocation. It looks that record up in Core on every request. Keys minted before the change were never registered, and the plan recorded the consequence as accepted: "Unregistered long-lived API JWTs are rejected. This includes legacy onboarding tokens" (docs/plans/2026-10-26-api-key-lifecycle-repair.md:35).

Longhand's tenant id, onboard-control-plane-at-technical-leaders-com, is the pattern the onboarding handler produces, and before this change that handler minted its key with SignAPIKey: subject equal to the tenant id, no credential kind (onboard.go:78 and :117 at 7e08966d). The new code classes such a key as a managed key (managed_keys.go:279), finds no record whose id is the tenant id, and answers 401 unregistered or revoked API key (managed_keys.go:235). Nothing checked which live clients held that kind of key, and nobody told Longhand.

Confidence: high on the mechanism. Not read: the claims inside Longhand's key (the secret was not opened) and the exact 401 body Longhand received, which no log retains.

Deploys outside main contributing

v124–v127 were built from local trees before #363 and #364 merged. v124's source is not on any branch: the first commit touching managed_keys.go is dated 19:49, after v124 went live at 18:56. Both PRs merged with zero reviews.

A health check that cannot see the failure contributing

Bluegreen cutover waits only for /livez, which needs no credential. The v129 machine was healthy by that check while it refused every client read. "No downtime" was reported for that deploy. That was wrong: clients were refused for 8 minutes.

4. The Core restart

Core runs as one machine with its data on a volume. Deploying it replaces that machine in place, and Core opens its port only after it has replayed its system streams into memory. On 21:02:08 that replay covered 2,751,968 events (2,740,641 of them tenant events) and stage 2 alone took 4 m 56 s, so AllSource was unreachable until 21:08:01. During that window the v127 control plane answered 401 rather than 503: its key lookup goes to Core, and an unreachable Core is reported as API key authority unavailable with the same 401 as a revoked key.

An earlier note already said a Core redeploy means platform-wide downtime. The zero-downtime procedure the team remembers having was not found in the repo's docs or history.

5. Why it lasted

  • No signal named the victim. Every denial is counted under tenant anonymous with no reason label, and the control plane writes no log line for a 401. Longhand disappearing looked like low traffic.
  • The verification checked one other tenant. The hosted proof reused "a separate existing tenant's credential" and never probed Longhand's. Its own post-rollout check recorded a 401 with cause "undetermined" and the rollout continued.
  • No alert exists on 401 rate. The only Prometheus alerts are four bandwidth rules.
  • v128 hid the problem. From 21:25 Longhand worked again, only because v128 did not contain the enforcement, so the merged code went out again at 22:44 with the same defect.

7. Actions

  1. Replace Longhand's key with a registered managed key and confirm reads through the new key before any enforcement is re-deployed.
  2. Do not re-deploy enforcement until a shadow-mode count shows zero would-be denials, or each denied tenant is listed by name with an owner and a date. Design in the companion report, section 5.
  3. Label every denial with tenant, credential kind and reason, and log it.
  4. Gate cutover on authenticated traffic: compare 401 rate on the new machine with the old before the old is stopped; roll back automatically on a jump.
  5. Alert when a tenant that was served flips to refused.
  6. Deploy only images built from merged main commits.
  7. Write down and restore the Core zero-downtime procedure, or change Core to open its port before replay and report not-ready until it finishes.

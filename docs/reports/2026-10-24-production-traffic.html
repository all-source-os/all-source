The 2026-10-24/25 outage

Added 2026-10-25, read between 10:30Z and 11:45Z from the allsource org's Fly Prometheus and Core's logs (the Application Logs datasource on fly-metrics.net). The charts in this section read data/2026-10-25-outage.js. Everything below this section is the report as read on 2026-10-24.

Two hours after the rest of this report was read, problems 4 and 3 combined into an outage. Core had been refusing to load one tenant for about 9 hours because it lacked the memory (4). Core was resized by hand at 21:51Z to make room, and the resize restarted it. On that restart, a write-ahead-log ordering defect in the system store (3) made Core refuse every egress reservation, so every read through the control plane failed for 12 hours and 7 minutes, until a fixed Core build started at 10:05Z on the 25th. No alert fired at any point.

Why every read failed

The control plane reserves egress bytes in Core's ledger before it returns a read, and completes the reservation after. The ledger lives in Core's system store, which is write-ahead-log only and never checkpointed (3). On every boot the log writer reopened the oldest segment and appended there. Recovery replays segments in name order, so the first entries written after a restart were replayed near the start of history, out of order. An egress Reserve or Complete replayed out of order fails, which invalidates that tenant's ledger account, and every later Reserve for it answers 503. This could happen on any restart; the 21:51Z restart is the one where it did.

The Core build fe6be49 (#351) recovers the system store in sequence order and moves the writer to a new segment after the highest recovered sequence. Its commit message records the mechanism.

Why nobody noticed for 12 hours

  • The only production alerts watched for too many bytes leaving the control plane. An outage that refuses reads lowers bytes, so the bandwidth alert went quiet. The outage looked like the bandwidth problem in this report fixing itself.
  • Core logged each refusal as 503 Service Unavailable latency=0 ms, with no reason, tenant or route. The control plane logs no request lines.
  • Fly did not scrape any AllSource metric (6), so there was no success-rate series to look at, only Fly's own edge counters.

Problems and bottlenecks

1. Longhand's control plane re-reads the same history bandwidth

Every hour, including every night hour, the control plane sends 1.6–3.5 GB to one caller in iad. Core answers 320 reads for every event written. The reads are whole histories fetched again: sampled response bodies repeat byte for byte (75,734 B for auth.member., 26,478 B for auth.org., 29,269 B for queue_binding.) minute after minute.

2. The egress guard throttles Longhand's reads and refuses most of its writes availability

Control plane v120 started at 15:40:36Z with the egress guard: one pool of 16 slots shared by every tenant, answering 429 when full (egress_guard.go:23,90-96). Successful requests from iad fell from about 21,000 to about 5,600 per 10 minutes, and 429s appeared. The guard treats every /api/v1/* route as billable (egress_guard.go:152-166), so writes compete for the same slots: 2,103 of 2,576 writes (81.8%) have been refused since 15:40Z. Whether Longhand retries a refused write was not visible from AllSource.

On Longhand's side, its own health endpoint reports the damage:

Sources: sum by (status)(increase(fly_edge_http_responses_count{app="allsource-control-plane"}[1h])); control_plane_http_requests_total; https://longhand-control-plane-api.fly.dev/health at 19:52Z. The 24-hour alert value falls only because these refusals remove traffic.

3. Every billed response writes two events into Core's system log, which is never checkpointed disk and memory

Each guarded response calls Core's egress ledger twice (reserve, then complete). Each call emits a tenant_events::UPDATED system event (event_sourced_tenant_repository/egress.rs) through append_system_event (event_sourced_tenant_repository.rs:229). The system store has no checkpoint or truncate path and keeps every event in memory (system_store.rs).

What happened next: at the 21:51Z restart, this log's append order made Core refuse every egress reservation for 12 hours. See the outage.

4. Core runs at 70–80% memory and refuses a tenant's hydration every five minutes capacity

Core uses 5.9 GB of 8.3 GB on average over three days, peaking at 6.7 GB. Its tenant cache accounts for 633 MB (allsource_core_cache_bytes), so most of the resident memory is something else, and the system store in 3 is one measured contributor. With about 2.4 GB available, Core refuses to hydrate decebal-dobrica-at-gmail-com, which needs 2.94 GB (16 × its 116.9 MB archive + 1 GiB reserve). That tenant's usage sync fails every five minutes and its quota meters stop reconciling.

Sources: fly_instance_memory_mem_total - fly_instance_memory_mem_available; Core /metrics; control-plane log archive_hydration_refused with needed_bytes=2943581248; hydration_admission.rs.

What happened next: the refusals were not limited to usage sync. Every read for that tenant failed from about 13:00Z, the Longhand control plane's tenant was refused from 20:17Z, and the resize meant to fix it triggered the outage.

5. The control plane is a shared-CPU VM that ran out of CPU credit under this load capacity

A shared-cpu-1x machine is guaranteed 6.25% of one vCPU (fly_instance_cpu_baseline = 0.0625) and bursts on a credit balance. Over three days the control plane averaged 6.73% busy, above its baseline. On 2026-10-21 from 19:00Z its balance sat at 0.5–17 and it was throttled 35–62% of every 10-minute bucket until 23:40Z, when Longhand's replay cache cut the response sizes. It is not throttled now, but it has no headroom: any return to that load throttles it again, and it has 256 MB of memory against a guard that can buffer 16 × 16 MiB.

Sources: rate(fly_instance_cpu{mode!="idle"}[10m]), rate(fly_instance_cpu_throttle[10m]), fly_instance_cpu_balance, fly_instance_cpu_baseline. Fly reports CPU time in centiseconds, so these rates read as percent of one vCPU.

6. What we cannot see observability

  • No metric carries a tenant or namespace label. Per-tenant bytes exist only as a frequency-biased log sample.
  • Fly does not scrape the control plane's /metrics (fly.toml has no [metrics] section), so its counters reset on every restart and have no history before 15:40Z today.
  • Per-tenant query counts exist in Core's usage records (the query meter flushes them), but reading them needs an admin credential that this report did not use.
  • The Longhand control plane runs in another Fly organisation, so its machine count, logs and retry behaviour were not read.

The schedule-tick question

An earlier draft recommended raising SCHEDULE_TICK_INTERVAL_SECS. That was not backed by a measurement, and it is withdrawn. The numbers:

Binding re-reads therefore cost 32 × 29,269 B × 1,440 passes = 1.35 GB a day per machine, and 1.35–5.4 GB a day for one to four machines: 2–8% of the 66 GB. A longer interval would lower AllSource's cost, not raise it, but it also delays schedules. Reading the bindings once per pass instead of once per org removes 31 of every 32 reads without changing schedule timing, so that is the change to make.

What to fix, in order

  1. Stop the guard from refusing writes, and make its slots per tenant. Writes carry no egress, yet 81.8% are refused (2). Exempt POST /api/v1/events from the egress slots, and replace the single pool with per-tenant admission so one tenant cannot starve the rest. Effect: Longhand's writes stop failing immediately, at no bandwidth cost.
  2. Stop writing two durable events per billed response. The ledger turns 23 reads a second into 17.5 system events a second that are never checkpointed (3). Lease bytes per tenant and settle in batches, and give the system store a checkpoint. Effect: system-log growth returns to the pre-15:39Z rate (one segment per 8–13 hours instead of every 30 minutes), and Core memory stops climbing with traffic.
  3. Give Longhand incremental reads, then move its polling onto them. 63% of bytes are time-bounded windows re-fetched in full (1). Positions from #345 and a conditional read (ETag/304 when nothing under the prefix changed) let a poll that finds nothing new return zero bytes. On Longhand's side: read forward from the last position, keep the window locally. Effect: bounded by the 63% share, about 41 GB a day at today's rate.
  4. Bound per-request authentication reads. Session histories (6%) and per-request RBAC and binding reads (12.7%) are re-fetched on every request. Bound the session read with an overflow fallback, memoise RBAC per request and invalidate it from events, and read bindings once per tick pass. Effect: up to about 12 GB a day at today's rate, plus 1.35–5.4 GB a day from the tick.
  5. Make the traffic visible. Scrape the control plane's metrics and add tenant and namespace labels, so the next report reads per-tenant bytes directly instead of inferring them from samples (6).

Expected effects are upper bounds computed from today's shares and rates, not forecasts of the post-fix rate.

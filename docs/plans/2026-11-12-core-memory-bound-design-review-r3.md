1. blocking I3 / S1 ledger + S4 query (design:214-217, :277-278, :356-359): I3 says DataFusion grow overshoot is "bounded by the query sub-budget", but the sub-budget gates only try_grow. grow is infallible, so operators that call it (EventQL joins and sorts over ResidentLedger) can exceed the cap without limit. Evidence: datafusion-execution-55.1.0/src/memory_pool/mod.rs:204 "/// This must always succeed", :205 fn grow; only :213 try_grow is fallible. DataFusion 55.1 operators call grow past budget: datafusion-physical-plan-55.1.0/src/joins/nested_loop_join.rs:1754 and sort_merge_join/materializing_stream.rs:999, :1108. Fix: name the mechanism that bounds operator memory (per-query try_grow pre-reservation wrapper per operator/stream, or a preflight estimate that refuses before execution), or remove "bounded". Add a test: a join under a small query sub-budget yields 503 or a ResourcesExhausted error, not overshoot. Sort uses spillable try_grow, so state the expected result per operator.

2. blocking S1 Reclaim step 4 / hydration, S1-S2 cold-read integrity (design:343-345, :361-362): hydration says it "records the archive generation at start and restarts if compaction changed it", but no archive-wide generation exists. cache_generations is per tenant and bumped only by try_evict_tenant (store.rs:2145-2152). Compaction takes only archive_mutation_guard (compaction.rs:756, archive_repack.rs:74, :289), which hydration never takes. The listing is taken once (storage.rs:1539). Non-strict load skips a file that vanished (storage.rs:1568-1587), returns complete=false (storage.rs:1600), and store.rs:1983-1984 marks the tenant loaded. Queries then serve partial results (store.rs:2469-2474), and is_loaded skips the completeness check on non-strict. The generation compare at store.rs:1951-1960 errors instead of restarting. Fix: define the counter (bumped by CompactionManager under archive_mutation_guard, read before and after each file, compared to the start value), or have hydration take archive_mutation_guard for its file walk. Treat a missing file as restart, not skip, on the non-strict path. Add a test: compaction removes a listed file between two hydration reads; assert restart or error, never a complete-looking partial.

If kept, state the ratio per stage and record MemAvailable and the refusal counter in the rehearsal evidence. If removed, move refusal to ArchiveHydrationRefused via the ledger.

6. blocking Measurement > Fixture (design:518-531, :542-545), Replay set (design:582-599), Replay driver (design:577): nothing makes replay deterministic in ids and timestamps. Event::from_strings assigns Uuid::new_v4() and Utc::now() (domain/entities/event.rs:153-159). The ingest handler uses it (infrastructure/web/api.rs:261-268), and IngestEventRequest has no id or timestamp field. The 12 canaries ingested in each run therefore get random ids and wall-clock times. Replay queries (order=desc&limit=1, event-type, time-window, limit=10000) can match them. Normalization covers only cursor and head epoch (design:596-597). query_digest_equal and replay_repeatable are hard gates (design:620-621), so they fail across processes. Fix: give canaries and fixture events fixed ids and timestamps from the seed through a seeded store path, or exclude canary-matching queries and say so. 7. should S1 Pins (design:321-329): the fast path takes the pin with no residency gate (store.rs:1875-1877 returns on is_loaded alone). try_evict_tenant takes gate.write before its pin check (store.rs:2127-2128). Fix: take the pin under cache_residency_gate.read, or specify ordering (evictor bumps generation before checking pins; reader increments pin before rechecking generation). 8. should S1 Followers (design:317-319) vs I3 (design:211-213) and brief:42-43: a read-only follower cannot evict (store.rs:2133-2135 returns false when read_only). Its replicated events are never written to Parquet (store.rs:1087-1091), so I4 blocks them too. Once its budget fills, ingest_replicated is refused permanently. The design says "apply stops and retries", but wal_receiver.rs:539-546 returns Ok without ACK and retries from the same offset, and the snapshot path (wal_receiver.rs:463-467) logs and drops the event. Fix: list followers as an explicit I3 exception with the replication-stall consequence, a lag metric, and an acceptance test (fill the follower budget, assert refusal count and lag, no eviction attempted). Specify the snapshot-path drop. Making flushed data evictable alone is not enough.

9. should S1 Reclaim step 2-3, no-WAL mode and I3 wording (design:209-218, :335-342, :351-354): a charge is refused when every resident victim is pending. Pending data drains only through checkpoint(), and checkpoint() returns Ok early without a WAL (store.rs:1540-1546). With WAL off there is no timer (store.rs:3338-3339; main.rs:198). With WAL on, the drain runs every 60 s. Storage flushes only at 10,000 events per tenant (storage.rs:342-347), so many small write-only tenants can fill the budget and stay refused for the whole interval. I3 names disk failure as the example, which is not exhaustive. No acceptance covers ingest availability under pressure. Fix: either trigger a flush for pending victims before the charge (outside every guard), with a bounded wait, or reword I3 and the embedded contract to say refusal lasts while data is pending, including no-WAL mode. Add a test: ingest into write-only tenants past budget, assert refusal duration is bounded.

10. should S1 Reserve-before-allocate owner table, index row (design:291-297, :304-309): index and entity_versions bytes are reserved in the per-event reservation before the WAL append. A failure at storage append (step 4), a WAL failure, or a VersionConflict refusal returns before index insert (step 5), leaving index bytes charged with no entry. Design:291 releases events.tail on request failure, but the index row has no such rule. The design does not say which owner holds the pre-insert index bound. Fix: state the owner of the pre-insert bound and add "request failure before index insert" to its release column. Add a test: fail the storage append, assert ledger total equals live bytes for that tenant. Impact is an overcount until eviction, which affects ledger_two_sided (design:623) only if that gate injects failures. It does not today.

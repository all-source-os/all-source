1. blocking Decision 15 cursors across restart (design:340-372; r14#2): WAL sequence counter resets to 0 on truncate, and the boot checkpoint truncates the WAL when recovered events are not yet in Parquet. New `ingest_seq` restarts low while persisted consumer cursors keep pre-crash values, so new events below the cursor are skipped. Events flushed by the boot checkpoint never enter the delivery log, so undelivered ones are lost. "WAL recovery restores it" (design:350-353) restores per-event seq only, not the counter. Evidence: wal.rs:271-272 (`*seq += 1`), wal.rs:758-763 (new WAL file, `*seq = 0`), wal.rs:692-693, store.rs:469 (`wal.recover()` drops sequence at call site), store.rs:567-575 (flush_storage, then `wal.truncate()` when buffered>0), store.rs:472-498 (recovered events pushed without delivery-log fill), api.rs:2236 (`cursor_position.unwrap_or(0)`), websocket.rs:143. Fix: persist a monotonic delivery sequence independent of WAL sequence, or floor the counter across truncate. State boot behaviour for events flushed before a crash. Add a restart test: crash with unflushed WAL, restart, consumer receives every post-restart event and every pre-crash undelivered event.

2. blocking Decision 15 delivery log memory and budget (design:354-362, 606, 449-475, 97-98; r14#2 vs I1/I2/I3): The log holds `Arc<Event>` per ingested event beyond eviction, charged to `delivery_log`, released only by cursor pass or the count cap (`ALLSOURCE_DELIVERY_RETAIN_EVENTS`, default 100,000, a count, not bytes). Eviction drops resident copies but the Arc keeps the allocation live, so eviction frees no heap for logged events. Design:361-362 "the log holds its own Arcs" is ambiguous: a separate allocation doubles heap, a shared one makes the ledger undercount. No victim releases log bytes. Refusal reasons (design:291-297, 450-455: tail_only, flush_failing, permanent, pinned) do not cover log-driven exhaustion, so ingest can stall with no reclaim path. Trim with zero registered cursors is undefined. `get_or_create` auto-registers any polled id with cursor None, pinning the minimum at 0. The I3 "Bounded overshoot sources" list (design:470) calls the log bounded, but the cap is a count and event size is not capped by design (2,048 B limit applies to three other routes only, api_v1.rs:219,228,237). The Amounts sentence (design:97-98) names only the event and its pending clone. Evidence: design:354-357, 361-362, 606, 291-297, 450-455, 470; api.rs:2215, api.rs:2235; consumer.rs:110-118. Fix: store a location pointer (seq to WAL/Parquet locator) instead of `Arc<Event>`, or charge the log to a named owner with a byte cap and a named refusal reason that reclaim can act on. Measure log bytes in S0 or move it to Unbounded known limits. Define trim with zero registered cursors. Update the Amounts sentence to name every owner of an ingested event.

3. blocking Decision 5 `query()` read unpinned (design:213-218, 244-253, 328, 1052-1054; r14#3, r14#4): `query()` is a caller that drops the guard before its read. The `ensure_tenant_loaded` match ends at store.rs:2488, and the events read is at store.rs:2516. A concurrent evictor can drop the tenant between them, so query returns a partial result with no error, violating I8 (design:519-521). The call-site list and reader table omit `query()`. Design:328 ("as event queries do") and the `pins_whole_reads` claim (design:1052-1054) are false for this path. Evidence: store.rs:2468-2488, store.rs:2516, store.rs:2545-2551. Fix: bind the pin across the read at store.rs:2516, including the `query_window_from_archive` path. Add `query()` to the call-site list and reader table. Correct design:328 or state the pin is held through the read.

4. blocking Decision 2 token compaction pin (design:106-108, 251; r14#11, regression): The design says the caller takes a ResidencyPin for "the token's tenant" through `ensure_tenant_loaded` before the query. The tenant is unknown until the query returns: `compact_tokens(&self, entity_id: &str)` takes no tenant, and the query runs with `tenant_id: None, limit: None`. The tenant is read from results at :325, and the cross-tenant check runs after the read (:326-332). Unfiltered queries do not load tenants and return degraded results (store.rs:2462-2467), so evicted durable tokens drop out of `merged_text` while phase 3 (store.rs:1440-1442) removes resident tail tokens. The merged derived output can be partial. Design:251 ("runs under its caller's pin and the gate") is false: the caller takes no pin and `compact_entity_tokens` takes no gate (store.rs:1405-1431). Evidence: embedded/core.rs:300, 306-317, 325, 326-332, 363; store.rs:2462-2469. Fix: pass `tenant_id` into `compact_tokens` (public signature change, not stated in design), resolve it before the read, call `ensure_tenant_loaded`, hold the pin across query, merge and `compact_entity_tokens`, and query with `tenant_id` Some. Add an acceptance test where the entity's tenant is evicted before compaction.

5. blocking Decision 15 cursor semantics and migration (design:358-360, 368-370, 974-983, 989-990): (a) "On S1's first boot, each one resets" has no detection mechanism. The persisted ack payload is `{consumer_id, position}` (consumer.rs:146-150), restore reads only `position` and merges with `if pos > current` (consumer.rs:236-240), so pre-S1 Vec offsets and S1 sequences cannot be told apart, and the reset cannot be made durable under the monotonic merge. (b) The default cursor for a new consumer is not stated: consumer.rs:20 documents `None` as "start from beginning", api.rs:2236 and websocket.rs:143 use `unwrap_or(0)`, and design:356-357 does not say whether `None` pins the trim minimum. (c) "redelivers at least once from there" does not say events between cursor and oldest retained are lost. Acceptance (design:989-990) asserts "A cursor past the cap gets 410" with no skipped range. Evidence: design:358-370, api.rs:2236, websocket.rs:143, consumer.rs:20, 146-150, 236-240. Fix: add a cursor format marker (in the ack payload or a versioned system event), define the `None` default, state the 410 gap as loss, and add a cap-overflow test asserting the 410 and the skipped sequence range.

6. should I3 refusal predicate and failure-mode text vs derived-only victims (design:450-451, 549-550 vs 240-241; r14#9 partially resolved): Victim eligibility now counts durable or derived bytes (design:130, 240). The refusal predicate ("every tenant holding durable resident events is pinned", design:450) and the failure-mode text ("No victim exists when every tenant with durable resident data is pinned, or when only tail data remains", design:549-550) do not. A derived-only unpinned tenant is an eligible victim that neither clause covers, so the text claims no victim when one exists. Evidence: design:130, 240-241, 450-451, 549-550. Fix: define refusal as "no eligible victim" per design:240, or add derived bytes to both sites (design:450 and 549-550).

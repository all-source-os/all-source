1. blocking Decision 5 cold path (design:153-156); acceptance pins_whole_reads named case r11#1 (design:863-864): Pin is taken before singleflight and returned by ensure_tenant_loaded, but the fast path returns Ok with no pin. A warm reader whose step-5 check fails on a generation change while loaded=true unpins, calls ensure_tenant_loaded, hits the fast path and reads unpinned. An evictor can then drop events mid-read, giving a partial result and breaking I8 (design:370-372). Evidence: store.rs:1874-1876 `if is_loaded() { return Ok(()); }` returns before budget (:1879), storage check (:1882-1888), lock_for (:1892) and any pin. Abandon restores loaded=true after the generation bump (design:137-139), so gen-changed with loaded=true is reachable. The r11#1 named case covers only hydrate-then-reclaim. Fix: take the pin at ensure_tenant_loaded entry, before the fast-path check. Re-check loaded under the pin. State that every return path (fast path :1876, no-storage path :1887, error path :1898-1903) returns a held pin, released by RAII guard. Make the r11#1 named case run through that entry.

2. blocking Decision 2 token compaction charge (design:93-96); owner table design:443; acceptance design:801-803; r11#3 fix: Charge is taken after the merged event is built, so bytes are resident before reservation. This contradicts Decision 2 first sentence (design:70-71, "Every path reserves before it makes bytes resident"). r11#3 asked for a reservation amount. v12 chose exact post-build size, which is not a reservation. Evidence: store.rs:1405-1409 `compact_entity_tokens(&self, entity_id, token_event_type, merged_event: Event)`. Caller embedded/core.rs:354-363 builds merged_text and Event::from_strings before the call. Design:93-96: "the charge is exact and is taken when compact_entity_tokens is entered". v11 (d0d5a3e) charged before build. Fix: reserve an estimate before the caller builds the merged event (state the formula) and reconcile to exact resident_bytes() in Phase 3 under the write lock (store.rs:1431). Or state the compaction build is an explicit bounded exemption from reserve-before-resident, add it to the I3 overshoot sources with its bound, and cite the exemption at design:70-71.

3. should Decision 5 warm protocol (design:141-152); pins_whole_reads (design:859-860): Release point for a warm reader's pin is not stated. Only the failure unpin is named (design:148-149). The cold path is explicitly held through its read (design:155-156). The warm path, the main path, is not. Evidence: design:141-149 ends at "takes the cold path" with no success-branch release. grep for unpin/release finds only :104, :148, :184 (hydration), nothing for warm reads. Named cases design:861-868 do not mention release. Fix: state that on success the warm reader holds its pin until its read returns, then unpins through a guard on every exit path. Add this to pins_whole_reads.

4. should Decision 5 and Decision 6 pin lifetime (design:153-156, 165, 170-171, 184-185): The delta extends pin lifetime to the caller's whole read and to hydration, which can run up to the 240 s timeout across three restarts. No release on error, cancellation or panic is stated. A leaked pin blocks eviction for the process lifetime (design:138-139 abandons on any pin), and under exhaustion that yields 503 (design:948). Evidence: store.rs:1898-1902 `lock.try_lock_for(timeout).ok_or_else(...)?` returns early, so a manual unpin after it is skipped. store.rs:1863-1871 admit_hydration `?` also exits early. The design names no guard type. grep of the design for guard/raii/unpin/drop finds no pin guard. Fix: require an RAII pin guard returned by ensure_tenant_loaded and held by the caller, with drop releasing on every path. Add an acceptance test that a timed-out, refused or cancelled load leaves pin count 0.

5. should Decision 5 per-tenant state, evictor steps and abandon path (design:129-140, 150-152, 865); r11#2 fix: The flag moves out of tenant_loader's DashMap<String,bool> (tenant_loader.rs:62), but the design does not say:
   - Which structure answers is_loaded, is_complete and pick_lru_excluding. Presence-based callers are store.rs:1871, 1907, 2094 (is_loaded), store.rs:2057 (pick_lru_excluding), and tenant_loader.rs:127 (iterates the key set). is_complete is at tenant_loader.rs:167-168, store_feed.rs:491. The entry stays present during evict, so these still read the tenant as loaded.
   - Whether success (step 4, "Drop the events") clears bytes and last_used. mark_unloaded does (tenant_loader.rs:181-185). Stale bytes keep feeding total_bytes (tenant_loader.rs:204).
   - Which tenant_loader methods begin_evict and abandon_evict call. Neither exists in apps/core/src. Abandon says "restores the captured loader state" without naming mark_loaded_with_integrity(captured) or mark_loaded. mark_loaded sets complete=false (tenant_loader.rs:163-165), which downgrades a complete tenant.
   - Whether restoring captured last_used is max() or a no-op. touch (tenant_loader.rs:111-113) is lockless on the warm path, so restoring an old Instant overwrites newer touches.
   Fix: name the single owner of loaded-ness after the move (the AtomicBool) and switch is_loaded, is_complete and pick_lru_excluding to read it. Name the tenant_loader methods used by begin_evict, abandon_evict and the success path. Abandon restores the integrity bit via mark_loaded_with_integrity(captured). Success calls mark_unloaded or a named replacement. State the last_used rule.

6. should Size bullet (design:45-53); I3 infallible owners; Decision 8 row projection.entity_snapshots (design:211): The added sentence "The rest are bounded by tenant count, event-type count or fixed capacity" is false. Overshoot list design:330-339 says infallible owners are bounded "as decision 1 states", but decision 1 gives no bound for it. Fix: move entity_snapshots into the distinct-entities bullet with embedded-only scope. Give its bytes-per-entry source or S0 measurement. Add it to the S0 measurement and I3 list. Delete the "rest are bounded" sentence or restrict it to the owners it covers. Not checked: whether Prime projections are entity-keyed (design:211 "other embedded or Prime projections").

7. should system_store Size (design:49-52); acceptance system_store_volume (design:809-811); I3 overshoot (design:331-332); Security (design:949-950); r11#7 fix: Partly resolved. No event-count bound is stated. The acceptance test is a one-year projection under 10% of budget, plus one write under pressure succeeding. It does not drive auth/audit volume at the measured rate and does not show the permanent refusal is unreachable. No action is named if the projection exceeds 10%. The 10% alarm is a warning only (design:54-55, :392). Growth beyond one year is unbounded because non-tenant domains never release (system_store.rs:98 `folded: &[SystemDomain::Tenant]`; fly-cost-reduction.md:102 "Their growth rate is not measured"). Design:56-58 still returns 503 on ingest on permanent exhaustion. The move-out alternative is untaken, and Decision 8 still lists system_store as infallible. Also, the Size bullet names six non-folded domains (Audit, Config, Schema, Policy, Consumer, Auth), but the acceptance test covers only auth and audit. Fix: either state an event-count bound (per-day volume times retention) or move system_store out of the permanent set. Name the action when the projection exceeds the threshold (e.g. S1 does not deploy). Widen system_store_volume to drive all six domains at the measured rate and assert no permanent refusal.

8. should Permanent-owner exhaustion threshold: brief item 8 (docs/plans/2026-11-11-core-memory-bound-brief.md:97-100); constraint 8 (design:391-393); Decision 1 (design:56-58); I3 (design:325-326); Security (design:949): Brief alignment (r11#6) is still incomplete. Decision 1 and I3 say "exceed the budget minus the query share". Constraint 8 and Security say "permanent owners alone fill the budget". Brief item 8 says "infallible owners alone fill the budget". Two builders diverge: at 80% of B, permanent set refuses under Decision 1 (80% > 75% at q=0.25) but not under constraint 8 until 100%. The brief also says "infallible" where the design says "permanent". Fix: pick one threshold (budget minus query share, per Decision 1 and I3) and use identical wording in constraint 8, brief item 8 and the Security line. Fix the terminology in the brief.

9. should Decision 2 token compaction charge (design:93-96); owner table design:443; constraint 9 (design:394-398): The compaction charge is refusable, since events.resident is not in the infallible table (design:206-213). The refusal outcome is unnamed. Constraint 9 lists only ingest, queries and hydration. Release is also unnamed when compaction exits early. Evidence: store.rs:1419-1421 `if !has_tokens { return Ok(false); }` runs after the charge is taken at entry. The charge is not transferred on that path. Design:80-81 "dropped if the request fails first" does not clearly cover a successful no-op, so builders can diverge (leak vs drop). Fix: state that a refused compaction charge returns an error from compact_entity_tokens (or skips compaction) and name the release on the Phase 1 no-op and on any Phase 3 failure. Add compaction to constraint 9 if a 503 is intended. Side note for item 2: design:94 cites the Phase 3 write lock at store.rs:1440; the actual `self.events.write()` is at store.rs:1431.

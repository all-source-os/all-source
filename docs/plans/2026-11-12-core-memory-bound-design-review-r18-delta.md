1. blocking Harness / Epoch normalization (design:380-381, :416-419): Normalization is response-side only. The feed epoch is a random 52-bit value per feed and gates cursor use, so a cursor with a different epoch is refused. A read-model commit built from the normalized head (epoch 0) is refused, and a request carrying the raw epoch varies across processes. The 52-bit assert from r17 #17 was dropped, and the constant-0 replacement can hide an epoch change. Evidence: apps/core/src/store_feed.rs:87 (`Uuid::new_v4` masked to 52 bits), :138-141 (epoch mismatch refused), :98-110; apps/core/src/store_read_model.rs:329-331 (commit epoch must equal head epoch); design:408 (commit from head in replay set). Fix: state that the driver keeps raw epoch values for every request, and that normalization applies only to digested response bytes. State that no digested path or body contains an epoch, including the VersionConflict body and the commit request's checkpoint.epoch. Restore the assert that each epoch is a 52-bit value (epoch < 1<<52) before replacing it with 0.

2. blocking Owner table, broadcast.store / broadcast.ws (design:261): One `Arc<Event>` is charged to two owners per push. Single-event paths send the same Arc to the store ring and the websocket ring, and each ring is charged per push. With zero receivers, tokio's `send` returns `SendError` without storing (tokio 1.54.1 src/sync/broadcast.rs:663-664), so the charge is never released. Websocket ring receivers exist only per connection, so with no WS or RESP clients the ledger grows by one event per push. That breaks the two-sided I2 bound (design:167-169). Evidence: apps/core/src/store.rs:761-764, :911-914, :1100-1103 (one Arc sent to both rings); :1027 (batch path sends a separate clone to the store ring only); websocket.rs:88, :132; resp/commands.rs:364; design:261 (v18 "per push", v17 "once at construction"). Fix: charge only when `receiver_count() > 0` at send time. Charge the shared Arc once under the store ring, and have the websocket ring count pointer size only. State which ring owns it. Re-check ledger_owns_heap (design:476-484) on the ingest path.

3. should Decision 2 / Acceptance evictions_match / Harness Eviction scenario (design:104, :318-322, :392-395, :430): The "available_bytes injected so the headroom trigger fires on a pinned schedule" claim has no seam. available_bytes() is a plain free fn, and on non-Linux it returns None, so has_headroom() fails open (is_none_or) on the darwin harness host. The headroom leg never fires. The oracle commit (design:318-322), Acceptance 1 (design:580-585) and the overlay list no injection point. The only named seam is file_namer. enforce_cache_budget does not need headroom to evict, since it evicts whenever over_budget. Evidence: apps/core/src/infrastructure/observability/memory.rs:21-23, :27-30, :84-86; apps/core/src/store.rs:2035-2041 (early return only if !over_budget && headroom); apps/core/src/infrastructure/persistence/tenant_loader.rs:93 (set_byte_budget is pub, used at store.rs:415); design:306 (aarch64-apple-darwin host). Fix: either drop "injected so the headroom trigger fires" and state that the eviction scenario is budget-driven with the headroom path untested on darwin, or add a named cfg-gated seam to the oracle commit and overlay and re-derive expected-evictions.txt from that build.

4. should Decision 2 (design:104) "locks all of this"; gate eviction_policy_unchanged (design:431, :98-101, :506): The digest set is "the decision-2 functions and constants", which is not enumerated and omits behaviour-determining callees. Not digested: TenantLoader::over_budget (tenant_loader.rs:102), pick_lru_excluding (tenant_loader.rs:125), memory::has_headroom and available_bytes (memory.rs:21-30, :84-86), reserve_from_env (hydration_admission.rs:65-66, which ALLSOURCE_MEMORY_RESERVE_BYTES overrides), the ALLSOURCE_CACHE_BYTES budget parse (store.rs:3254, :3314-3330), and estimated_size_bytes (event.rs:307). On darwin the headroom branch is a no-op, so a mutation there passes every gate. The negative control (design:506) covers only the named eviction functions. Evidence: as listed. Fix: enumerate the digested items by path, add each missing function with its own negative control, or reword design:104 to name exactly what is locked.

5. should Decision 2 wording vs S1 owner table (design:96-97, :101-104, :253-260, :330, :335): Decision 2 says today's eviction code "stays exactly as it is" and "the ledger only observes it". The owner table makes S1 edit try_evict_tenant with ledger releases. The eviction_policy digest is frozen at step 4 (design:330, :335), after those hunks, so it locks S1 code and not f4b53930. Only evictions_match (design:430) checks behaviour against f4b53930. Evidence: apps/core/src/store.rs:2158 (events.retain), :2159 (feed_indexes.remove), :2177-2193 (index clear and rebuild), all inside try_evict_tenant (store.rs:2127-2223). Fix: reword Decision 2 to "behaviour unchanged; code changed only by the listed ledger calls". State that the digest freezes after the step-4 hunks and that behaviour equality with f4b53930 is evictions_match. Or freeze the digest at the oracle commit and list the S1 hunks separately.

6. should S1 owners / Decision 1 measurers (design:86, :167-169, :233, :428): "Maps and vectors: capacity times entry size" leaves entry size undefined. Under a shallow reading it excludes owned key and value heap. Index maps are DashMap<String, Vec<IndexEntry>> and DashMap<Uuid, usize>, so each entry's String key heap and Vec heap are uncounted. The same applies to entity_versions and version_index_*. The Events measurer (design:81-84) is defined, but the index maps are not. The S0 split (design:233) is aggregate only, not per owner class. ledger_two_sided (±10%) and I2 depend on this. Evidence: apps/core/src/infrastructure/persistence/index.rs:39-45; brief line 19 (~61,600,000 bytes for indexes). Fix: define entry size in design:86 (size_of plus an owned-heap walk, or a named per-map measurer). Add a per-owner-class estimator-error row to the S0 split at design:233.

7. should Acceptance 5 (design:600-606, r17 #6): The post-deploy criterion `|allsource_heap_unattributed_bytes| / allsource_heap_live_bytes ≤ 0.10` has no failure action. Nothing says what happens if it is exceeded, if snapshots are still listed, if geo is not tenant-scoped, or if the eviction rate changes (:605). S0 gating (design:37-43, :586-587, :614) covers only the pre-S1 state. Delivery (:618) says "deploy on the user's go". Rollback exists only as I6 and Acceptance 6 (design:192, :607) and is not linked to Acceptance 5. Two builders could diverge on whether a miss reverts the deploy, re-approves the owner table, or accepts drift. Fix: state the action, decider, and whether design approval reopens for each Acceptance 5 failure. Name which measure (ledger gauge at design:94-95, or site-based jemalloc at :232) each threshold applies to.

8. should Harness / Runtime determinism (design:373-374): v18 extends the driver-only rule to "no checkpoint_at_boot, no spawn_memory_upkeep, no clock, no random id and no timer" for the whole replay. This is false for Core. LRU victim order uses Instant::now on touch (tenant_loader.rs:112, :173; pick_lru_excluding :125-149; picked at store.rs:2057). Feed epoch uses Uuid::new_v4 (store_feed.rs:87). The flush path write_tenant_events uses Utc::now and a Uuid in the file stem (storage.rs:553-566, called from :488). The month partition dir uses Utc::now (storage.rs:1839-1845). Ties in LRU fall back to DashMap iteration order, which is randomised in production. file_namer (design:184-186) covers file names but not the month partition dir. Fix: restore the v17 driver-only scope, or list each Core-internal clock and random source with why it is harmless. Inject an LRU sequence counter, and state that flush partition month and file stem are not digested.

9. should Decision 5 (design:110-115); Harness tenant_scope_geo (design:490-495, :573): The tenant filter on geo candidates is not implementable as written. GeoIndex has no tenant: grid is DashMap<(i32,i32), Vec<(Uuid, Coordinate)>> and coordinates is DashMap<Uuid, Coordinate>. Candidates come only from geo_index (geospatial.rs:320-340), and the tenant filter applies to events after the candidate map is built (:349-366). design:114-115 says the design "filters geo-index candidates to that tenant before building the candidate map", which the current code cannot do. Also, the no-spatial-filter branch (:330-340) scans all geo_index.coordinates regardless of tenant. Fix: state the real mechanism. Either filter resident events by tenant before building the map (state that the global scan cost remains), or add tenant to GeoIndex and charge it as an owner. Then tenant_scope_geo can be tested as written, and "geo tenant scope | rock" (design:573) is supported.

10. should Decision 3 (design:105-106) vs owner table (design:257, :264): Decision 3 says never-released owners are summed in allsource_core_permanent_bytes. Code agrees it is never removed (store.rs:206, :381, :1925, :1952, :2146-2152). The map is small, so this is not blocking. Fix: add cache_generations to the permanent row at design:264, or name the set in Decision 3.

1. blocking Decision 5 (design:116-135) and acceptance pins_whole_reads (design:809-812): the reader protocol covers only the warm path. The cold path ("takes the cold path", design:131-132) is unspecified after `ensure_tenant_loaded` returns, and the hydrating pin's lifetime is unstated ("The hydrating tenant is pinned", design:161). Interleaving: R hydrates A, the pin is released, a reclaim for B evicts A (sole durable victim), the evictor clears `loaded` and bumps the generation, R reads A and gets a tail-only or empty result, breaking I8 (design:341-343). Evidence: store.rs:2469-2474 (`ensure_tenant_loaded` Ok then touch, no pin or generation check), store.rs:2516 (`let events = self.events.read();` with no pin), design:100 ("rehydrates and merges the tail", no re-entry stated). Fix: state that the cold path re-enters steps 1-5 after hydration, or holds the hydration pin through the read. Add the hydrate-then-evict-before-read case to pins_whole_reads as a named interleaving. Also fix the false "No interleaving yields a partial result" claim at design:810, which covers only the warm order.

2. should Decision 5 step 3, "restores the loaded flag" (design:122; pin restore at design:812): no restore primitive is named. `mark_loaded` sets `complete=false`, so a restore through it downgrades a complete tenant and forces a full reload. `mark_loaded_with_integrity(true)` would clear a partial (corrupt-file) tenant's integrity. Bytes and `last_used` are lost if step 1 uses `mark_unloaded`, though the design does not say which clear primitive it means. `pick_lru_excluding` skips loaded tenants without a `last_used` stamp. Evidence: apps/core/src/infrastructure/persistence/tenant_loader.rs:62, :132-141, :163-165, :172-175, :181-185; store.rs:1883-1886, :1983-1984. Fix: name a tenant_loader abandon-restore method that reinstates the captured integrity bit, `last_used` and bytes under the still-held residency gate.

3. should Owner table `events.resident` (design:414), Decision 2 amounts (design:78-83), I1 (design:285-286), acceptance compaction_releases_tokens (design:764-766): the merged derived event is charged both as "exact resident_bytes()" and as "charged from that compaction's reservation, taken before it is built". The reservation size is never named, and Decision 2 has no token-compaction amount. No reconcile point is named for the derived charge; the "same critical section" wording attaches to the removed-token release. I3 (design:307) lists compaction as an overshoot source with no reconcile. Evidence: store.rs:1395-1449 (`compact_entity_tokens` takes an already-built `merged_event`); the Phase 3 write lock near store.rs:1440 is the natural reconcile site, which the design does not state. Fix: name the reservation amount (estimate formula or exact pre-build size), add compaction to the Decision 2 amounts list, and name its reconcile point.

4. should Decision 1 boot check (design:55-58), acceptance boot_refuses_budget_over_machine (design:769-770): the design says machine memory is "cgroup memory.max when set, and physical RAM otherwise, read by the existing observability/memory.rs reader". That reader returns available bytes, not total: `cgroup_v2_available = limit.saturating_sub(current)` and `host_available` reads MemAvailable. Non-Linux returns None, and memory.rs:25-26 says None means do not refuse. No total-memory reader exists in apps/core, crates or tooling. The design also does not say what the boot check does on an unknown value, and the evaluators run on darwin (design:511), so the undefined branch is on the main dev path. Evidence: apps/core/src/infrastructure/observability/memory.rs:21-55. Fix: add a total-memory reader (cgroup memory.max with "max" as unlimited, else MemTotal, else sysctl hw.memsize). State refuse vs skip-with-warning on None, and say which one the darwin test uses. Do not cite the existing reader.

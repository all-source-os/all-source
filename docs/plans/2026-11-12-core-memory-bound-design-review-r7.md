1. blocking Decision 1, Decision 8, I3, Security (design:36-41, 97-99, 192-196, 594-595): permanent owners (entity_versions, version_index_*) count against the one budget, are charged infallibly, and are never released. I3 lists refusal causes as pinned/not-durable/flushing only, and Security says permanent owners never cause 503. Permanent growth alone can exceed budget minus charge with zero victims, and every later charge then refuses with no listed release. No stated ceiling (only "bounded by distinct entities"). Evidence: design:40-41, 97-99, 196, 514-515 (test `permanent_owners` asserts "never refuses" only), 594-595; store.rs:173, 677, 1765, 1149; try_evict_tenant (store.rs:2127-2223) never removes entity_versions or version_index_*. Today 3,875,710 B / 35,936 entries (~108 B/entry), so reaching a 5 GiB budget needs ~50M distinct entities. Far off, but I3 as written is false. Fix: add a permanent-owner ceiling, or add "permanent owners alone exceed budget" to I3 refusal conditions and Security with the consequence (ingest 503 until restart or budget change) and an alarm metric. Delete "Permanent owners never cause it" unless a bound is stated and tested. Also closes r6#1.

2. blocking Decision 2 amounts vs owners table (design:56-61, 268-269, 282-288): ingest reservation omits the pending copy. Step 1 charges only the event's resident_bytes() plus index bound. storage.pending (a second full copy, held until flush) is charged "at storage append", step 4, with no reservation. Pending copy is therefore outside the budget until after it is resident. Evidence: store.rs:1019 `storage.append_event(event.clone())` runs before `events.push` (:1030); storage.rs:336-341 pushes into current_batches, held until flush (batch_size default 10,000, storage.rs:123). Fix: step 1 reserves event + pending together, split per owner at transfer, released on storage failure. Add pending to the amount list and ingest-order section. Test: write-only tenant with pending events, ledger total covers events + pending within 10%.

The replay driver goes through Core's full v1 router, and build_v1_router is an oracle-only move (design:213-214). build_v1_router does not exist on f4b53930 or origin/main; the f4b53930 router is inline in serve_v1 (api_v1.rs:151, :185), which returns no Router. f4b53930 also has no deterministic-hash feature or HashState (grep of apps/core Cargo.toml and src empty). The cold-load anchor (design:444, a hard gate) has no build recipe. Acceptance 4 cannot be produced as decided. Fix: state the overlay recipe: file list (harness example, fixture writer, driver, tie-break sorts), ported moves (router extraction, or serve_v1 loopback), hasher port or omit, Cargo.lock; define the anchor build and phase as a frozen manifest argument. Or drop the overlay from Acceptance 4 and record I5 as oracle-relative only.

5. blocking Decision 4 eviction gate; I3 flusher claim (design:74, 76, 94-96, 194-196, 512-513, 594): eviction requires not_durable == 0 and flushing clear. The flusher clears a tenant only when its writes stop, since appends after a flush take re-pend it. Under steady writes into every resident tenant, the count stays non-zero at each reclaim, so refusal persists while writes continue. Brief Goal says "reclaim cannot be refused forever" (brief.md:43-44). Test flusher_bounds_refusal (design:512-513) uses write-only tenants and does not cover concurrent appends. Evidence: store.rs:668 (ingest takes cache_residency_gate read), store.rs:2127 (reclaim takes write). Fix: state the liveness condition precisely (refusal lasts while every resident tenant is written, pinned or flushing), or add a bounded mechanism (flush-then-retry, or least-recently-appended victim selection with bounded wait). Add test: concurrent appends to all resident tenants past budget, assert refusal count bounded or ingest admitted within N ticks.

6. should Decision 5 (design:81-83); pins_whole_reads (design:526-527): Dekker protocol needs SeqCst on pin increment, generation read, generation bump, and pin read. 9. should Ingest order, ingest_batch prefix (design:295-298; acceptance storage_failure_after_wal design:497-499): WAL append covers the whole batch before any per-event step (store.rs:992-996, phase 3 at :999). 10. should Decision 1 query sub-budget (design:38-39); Decision 3 (design:65-68); I3 (design:192-196): query.* is capped at fraction q. A query refused by the q-cap is refused with victims present, and evicting victims frees total bytes, not the query share. Decision 3 runs reclaim on any refused reservation, query included, and the stop predicate is undefined (eviction loop stops on satisfied(), store.rs:2055-2078). A q-capped query can drain the evictable cache. I3's refusal list does not name this case. No test covers it (design:507, 515-518). Fix: q-cap refusal triggers no eviction; reclaim stops at total-budget fit; add q-cap refusal to I3 with its 503 consequence; test: query over q-cap with unpinned victims returns 503 and evicts nothing.

11. should Decision 1/3 with no archive (store.rs:309, 1882-1887, 2129-2132; I3 design:192-196): storage-less stores have no archive, try_evict_tenant returns false, so there are no victims. Design does not say whether the budget applies. Fix: state the budget is unenforced without an archive (I2 still counted), or that refusal is permanent in that mode; amend I3; add a named test.

1. blocking Decision 15 deploy gate (design:371-394; constraint 12 design:571-575; acceptance deploy_gate_no_cursors design:997-999): the gate is point-in-time and its count misses cursors. (a) Consumer and websocket cursor routes stay live after deploy and nothing refuses them or re-checks. An unknown-id poll or ack calls `get_or_create`, creating a consumer with cursor None or a Vec offset (`unwrap_or(0)`), re-entering the r15#1/#2/#5 skip/repeat failure. (b) The gate reads the system store Consumer domain, written only by `register()` (consumer.rs:89) and advancing `ack` (consumer.rs:146). `get_or_create` (consumer.rs:110-119) writes nothing, so poll-only and websocket-replay-only consumers are invisible. (c) The websocket predicate is undefined: `receiver_count` counts every event_tx receiver, including RESP3 SUBSCRIBE, so it over-blocks and is not the cursor predicate. Evidence: api.rs:2215 and :2235 `get_or_create`; api.rs:2236 `unwrap_or(0)`; websocket.rs:140-141 replay on consumer_id; websocket.rs:431 `receiver_count()`; websocket.rs:94-95 and commands.rs:364 `subscribe_events`; api_v1.rs:443-453 routes; design:272 "keeps them out of use" has no runtime mechanism. Fix: either the S1 build refuses (409 or 503 with reason) consumer and cursor-replay routes until the cursor revision lands, or the gate is re-run at deploy with an alarm on consumer count > 0. Define the predicate: count `get_or_create` entries with cursor_position set, or a poll or websocket in the window, using the in-memory registry (`ConsumerRegistry::count`, consumer.rs:172) and the websocket manager, and record it in the S1 report. State that a post-deploy poll is not covered by the pre-deploy check. Make deploy_gate_no_cursors a deploy checklist item, not a unit test (it sits in the acceptance-tests section at design:997-999).

2. blocking Decision 15 search bullet (design:389-392); readers row (design:265); constraint list (design:539-575): mechanism is reversed and "loses nothing" is false. Eviction shrinks total_events, which lowers the left side of the rescan trigger (event_search.rs:185, :200), so eviction suppresses rescans and cannot start one. Hydration splices grow total_events with no broadcast (append_loaded_event store.rs:2259-2288; broadcast sends only at store.rs:762, 912, 1027, 1101). Repro: ingest 100 (expected=100), evict 50 (total 50, ids removed), rehydrate 50 (total 100). 100 > 100 is false, so no rescan runs and the 50 rehydrated events stay unindexed until restart. v15's "indexes hydrated events at splice time" was deleted with no replacement; r15#9 is resolved wrongly. Also, event_search.rs:375 skips ids in `state.indexed`, which is only extended (:411) and never pruned. Once design:392 removes an evicted id from the index, a rehydrated event is skipped by index() and stays unsearchable. Search is resident-only (event_search.rs:356-365, no ensure_tenant_loaded), so search results for evicted tenants change; that change is not in the constraint list. Evidence: event_search.rs:185, :190, :193-200, :215, :356-365, :375, :411; store.rs:762, 912, 1027, 1101, 2259-2288. Fix: delete "loses nothing" and the "not needed" claim, and correct the direction of the total_events effect. Name a replacement trigger (index hydrated events at splice time, or rescan on resident-set change) and record it. Prune `indexer.indexed` on eviction. Add a test: evict, rehydrate, then search finds the rehydrated events. Add search-result change under eviction to the constraint list or to I5 exclusions.

3. blocking Decision 5 retired-counter row `over_budget` (design:180): maps to `ResidentLedger::try_reserve`, whose refusal runs reclaim (decision 3). Evidence: design:130-138, 180; store.rs:2036-2084. Fix: map the predicate callers (2036, 2040, 2049, 2052) to a non-reserving `ResidentLedger::over_budget()` or `total() > budget()`; map only the reservation sites to `try_reserve`; state how `has_memory_headroom` is treated. `ledger.rs` is new in S1 (design:184), so these names are design-only.
